## 2. Розподіл вимог для покриття (SRS v1.1)

Оскільки в команді один **Тест-аналітик**, усі вимоги передаються йому для опрацювання та покриття у `test-cases.xlsx`:

*   **Функціональні вимоги для покриття кейсами:** 
    *   F-10 (Реєстрація), F-20 (Вхід), F-30 (Відновлення доступу), F-40 (Огляд рахунків), F-50 (Деталі рахунку), F-60 (Відкриття рахунку), F-70 (Переказ коштів), F-80 (Оплата рахунку / Bill Pay), F-90 (Пошук транзакцій), F-100 (Оновлення контактів), F-110 (Заявка на кредит), F-120 (Вихід), F-130/F-140 (Служба підтримки).
*   **GUI-вимоги (GUI-10...GUI-80):** 
    *   Перевіряються паралельно з функціональними. ТА має інтегрувати їх у відповідні тест-кейси (наприклад, перевірка обов'язкових полів під час реєстрації за F-10).
*   **Непокриті вимоги (BL-10...BL-80, NFR):** 
    *   ТА вносить їх в аркуш *Coverage* із вказанням причини: *"Вимоги BL покриваються юніт-тестами у Спринті 4; нефункціональні вимоги (NFR) перевіряються оглядом"*.

## 3. Схема ідентифікаторів та правила комітів

**Ідентифікатори артефактів:**
*   **Тест-кейси:** `TC-001`, `TC-002`, `TC-003`... (використовуються на аркушах *Test cases* та *Run 1*).
*   **Дефекти (Bug Reports):** `BUG-001`, `BUG-002`, `BUG-003`... (використовуються в GitHub Issues та у колонці Bug ID).
*   **Скріншоти:** `BUG-001-1.png`, `BUG-001-2.png`... (зберігаються у папці `attachments/`).

**Правила найменування комітів:**
Коміти мають бути зрозумілими та відображати суть змін. Рекомендований формат: `[Type] Description`.
Приклади:
*   `[Docs] Add task-board.md and distribute sprint tasks`
*   `[Test] Add 20 draft test cases for functional and GUI requirements`
*   `[Test] Complete test cases review, update status to reviewed`
*   `[Bug] Add bug reports BUG-001 to BUG-005`
*   `[Docs] Update execution log and add final sprint statistics`
